# PLAX 六模型推理性能优化方案

- 文档状态：P0 可观测性代码已实施、待服务器复测
- 编制日期：2026-08-21
- 适用范围：单张 PLAX DICOM 的 LVID、IVS、LVPW、LA、Aorta、AorticRoot 六模型串行推理
- 当前决策：暂缓直接采购或迁移 GPU，先补齐阶段计时并验证持久推理进程方案
- 非目标：本文不修改算法代码、不改变既有任务历史版本、不替代临床结果一致性验收

## 1. 目标

在保证六项测量结果、错误语义、算法版本和历史任务均不被破坏的前提下，定位 PLAX 约 40 分钟耗时的真实构成，并按证据选择以下优化路径：

1. 消除重复的 Python/PyTorch 启动和可复用的数据准备开销。
2. 判断模型前向推理、模型加载、DICOM 处理和视频后处理各自占比。
3. 先完成 CPU 侧架构优化，再以同一 DICOM 做 CPU/GPU 对照试验。
4. 建立可重复、可审计的冷启动和热启动基准。

性能目标需由产品或临床场景最终确认。工程上暂以整例 PLAX 不超过 10 分钟为第一阶段目标，以不超过 5 分钟为探索目标；在正式确认 SLA 前，这两个数字只用于评估优化收益，不作为发布承诺。

## 2. 当前基线与已证实事实

### 2.1 AorticRoot 单模型

| 项目 | 结果 |
| --- | --- |
| 总耗时 | 386.367 秒 |
| 输入帧数 | 94 帧 |
| 超时 | 否 |
| 运行设备 | CPU |
| 权重匹配 | 完整匹配 |
| 进程树峰值 RSS | 1737.19 MB |
| 输出 | AVI、坐标 CSV、距离 AVI、距离 CSV 均生成 |

采样末段约 10.6 秒、约 8.9 帧/秒的进度条来自 `process_video_with_diameter()`，对应距离标注视频的逐帧绘制与写出，不是模型神经网络前向循环。当前证据不能证明“实际模型推理仅 10.6 秒”，也不能把其余约 375.8 秒全部归因于 Python 启动、PyTorch 导入和模型加载。

单模型采样期间，子进程累计 CPU 时间与墙钟时间接近，且总 CPU 占用表现接近单个逻辑核心持续工作。这说明存在明显的单核 CPU 密集阶段，但在补充阶段计时前，无法判断该阶段属于模型前向、DICOM/图像处理、视频编码或其他操作。

## 3. 当前结论

“先优化执行架构，再决定 GPU”方向可行，但不能以“97% 都是初始化”为依据。当前更准确的结论是：

- 六个模型各自启动独立 Python 子进程，确实存在可消除的重复工作。
- DICOM 解码、resize 和输入张量构建具备跨六模型复用的可能。
- 单模型约 6 至 7 分钟的具体阶段分布尚未测出，模型前向仍可能是主要瓶颈。
- GPU 迁移与持久进程不是互斥方案；若前向推理占比高，两者可能需要组合。
- 直接确定 8–12 GB 显卡采购规格证据不足，必须先测单模型和六模型的显存峰值。

因此，正式 GPU 决策状态为：**暂缓，等待阶段计时和持久进程基准。**

## 4. 待验证假设与判定门槛

按优先级验证以下假设：

1. **模型前向占主导。** 若六模型累计 `inference_seconds / duration_seconds >= 50%`，应优先测试 GPU、CPU 线程配置或两者组合。
2. **导入和模型加载占主导。** 若 `python_import + model_construct + checkpoint_load >= 50%`，持久进程与预加载将是首选。
3. **DICOM、输入处理或视频后处理占主导。** 若这些阶段合计超过 20%，优先复用输入、减少重复视频生成或把展示视频异步化。
4. **CPU 线程或运行环境限制吞吐。** 若模型前向耗时高且进程始终只占用一个逻辑核心，检查 PyTorch 线程数、进程亲和性、OMP/MKL 设置和实际 CPU 能力。
5. **磁盘、杀毒软件或冷缓存造成额外延迟。** 对同一输入分别执行一次冷启动和至少三次热启动，并记录磁盘读取量和阶段耗时；若差异显著，再处理存储或安全软件白名单问题。

## 5. 第一阶段：只增加可观测性

在改变执行架构前，为 `inference_2D_image.py` 增加单调时钟阶段计时。每个模型至少记录：

- `process_start_seconds`
- `python_import_seconds`
- `model_construct_seconds`
- `checkpoint_read_seconds`
- `state_dict_load_seconds`
- `device_prepare_seconds`
- `dicom_decode_seconds`
- `resize_seconds`
- `tensor_prepare_seconds`
- `inference_seconds`
- `primary_video_write_seconds`
- `coordinate_csv_write_seconds`
- `distance_compute_seconds`
- `distance_video_write_seconds`
- `distance_csv_write_seconds`
- `postprocess_seconds`
- `duration_seconds`

同时记录：

- `task_id`、`asset_id`、模型名和不可变算法版本。
- DICOM 文件 SHA-256、帧数、原始分辨率和处理后分辨率；不得记录患者身份字段。
- Python、PyTorch、torchvision、CUDA/cuDNN 版本和实际设备。
- `torch.get_num_threads()`、`torch.get_num_interop_threads()`、CPU 逻辑核心数和进程亲和性。
- 进程树峰值 RSS、CPU 时间、读写字节数和退出码。
- 任务提交、开始、完成时间及最终状态。

计时应使用 `time.perf_counter()`，日志同时写入结构化 JSON。一次模型运行的所有阶段之和应能与 `duration_seconds` 对账；允许存在少量未归类开销，但差额应低于总耗时的 5%。

### 5.1 监控数据质量规则

- 每次运行使用新的输出目录和 JSONL 文件，不追加历史采样。
- 启动监控前验证根 PID 存在，且不得为 0、4 或操作系统保留进程。
- 记录服务 PID、推理子进程 PID 和父子关系，不按名称猜测进程归属。
- 只有最终任务为 `completed` 或明确的失败终态时，摘要才可标记为完整。
- 监控中断时明确写 `partial=true` 和已覆盖的模型范围。

## 6. 第二阶段：持久推理 Worker 与输入复用

### 6.1 推荐架构

新增独立的 Measurement 持久推理 Worker，由服务通过本机 IPC 或受控任务队列调用：

```text
HTTP 服务 / 任务队列
        |
        | task_id、DICOM 路径、模型列表、输出目录、算法版本
        v
持久 Measurement Worker（单任务串行）
        |
        +-- Python/PyTorch 只初始化一次
        +-- DICOM 只解码、resize、构建输入张量一次
        +-- 按固定顺序运行六个模型
        +-- 先生成结构化数值，再生成或排队生成展示视频
```

不建议把六个 PyTorch 模型直接加载进 Uvicorn Web 进程。独立 Worker 可以保留崩溃隔离、超时控制、进程重启和服务轻量化，并便于后续切换 CPU/GPU。

Worker 必须保持当前单实例、单任务执行边界，首轮优化不得同时扩大并发数。

### 6.2 两种模型驻留策略

先比较两种策略，不预设六模型全量预加载一定更优：

| 策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 单模型槽 | 网络结构和 Python 进程复用，依次加载六个权重 | 内存较低，改造风险较小 | 仍有六次 checkpoint 加载 |
| 六模型预加载 | Worker 启动时加载六个模型并常驻 | 热任务延迟最低 | 内存或显存需求高，启动恢复更慢 |

单个 AorticRoot 进程树峰值已约 1.74 GB，不能简单乘六推导常驻内存，但也不能假定服务器可容纳六模型。测试顺序应为单模型槽、同时驻留两个模型、再尝试六模型，并逐步记录 RSS/显存。

### 6.3 行为与可靠性要求

- 固定模型顺序：LVID、IVS、LVPW、LA、Aorta、AorticRoot。
- 每个任务开始前清理上次任务的输入引用、临时输出和模型状态，禁止任务间数据串扰。
- 输出采用任务专属目录，写临时文件后原子替换最终文件。
- 模型级和任务级均保留超时；超时或崩溃后由管理进程终止并重建 Worker。
- Worker 启动时校验模型文件、模型哈希、运行环境和算法版本，拒绝 `unknown`。
- 每个结果绑定任务创建时的算法版本；部署新版本不得重写旧任务记录。
- 提供 CPU 回退路径。建议以配置项控制 `subprocess` 与 `persistent` 两种模式，便于灰度和回滚。

## 7. 第三阶段：结构化结果与展示视频解耦

当前距离标注视频会执行逐帧 Matplotlib 绘制和视频编码。若阶段计时证明视频后处理占比较高，可将任务拆分为：

1. 优先产出坐标 CSV、距离 CSV 和临床结构化数值。
2. 结构化结果通过一致性校验后，诊断结果进入可审核状态。
3. 展示 AVI 作为独立后台产物生成，并使用单独的 `videoStatus` 或等价状态字段。

这一改变涉及 API 契约、门户展示和临床工作流，实施前必须明确：

- 临床审核是否依赖标注视频。
- 视频未完成时任务是否允许显示为 `completed`。
- 视频失败是否应使整个诊断失败，还是仅标记附件生成失败。

在契约确认前，距离 CSV 和当前六项结构化输出仍为同步必需产物，不得为了提速直接跳过。

## 8. 基准测试矩阵

使用同一份去标识化 PLAX DICOM、相同权重和相同算法版本执行以下对照：

| 方案 | 冷启动 | 热启动 | 目的 |
| --- | ---: | ---: | --- |
| 当前六子进程基线 | 1 次 | 3 次 | 建立可复现基线 |
| 持久 Worker + 单模型槽 | 1 次 | 至少 3 次 | 验证导入、输入复用收益 |
| 持久 Worker + 六模型预加载 | 1 次 | 至少 3 次 | 验证延迟与内存权衡 |
| 优胜 CPU 方案 + 异步视频 | 1 次 | 至少 3 次 | 评估结构化结果首屏时间 |
| 优胜方案的 GPU 版本 | 1 次 | 至少 3 次 | 仅在进入 GPU 门禁后执行 |

每次运行至少保存：

- `plax-stage-timings.json`
- `plax-run-summary.json`
- `plax-process-tree.jsonl`
- 六个模型的完整 `duration_seconds`
- 整任务提交到完成的总耗时
- 进程树峰值 RSS；GPU 试验另存显存峰值和利用率
- 最终 API 响应和六项结果摘要

冷热运行不得混用同一个汇总统计。报告应给出热启动至少三次的中位数、最小值和最大值。

## 9. 验收标准

### 9.1 功能与版本

- 正常 PLAX 任务最终为 `completed`。
- 六个模型均有 `duration_seconds`，六项临床结构化结果齐全。
- `cardiacUltrasound[0].error=null`。
- 新任务显示正式发布版本且不为 `unknown`。
- 旧任务仍显示创建时版本，发布和重启后不得被改写。
- 当前模式与优化模式在同一 DICOM 上的坐标、距离和结构化结论保持一致；数值容差由算法负责人签字确认。

### 9.2 性能与稳定性

- 第一阶段暂定目标：正常 94 帧 PLAX 热启动中位数不超过 10 分钟。
- 探索目标：不超过 5 分钟；只有在临床或产品确认后才升级为硬性 SLA。
- 连续运行至少 10 个任务，不出现 RSS 持续单调增长、模型串扰或临时文件串扰。
- 人工终止 Worker 后可自动重建，下一任务可成功执行。
- 任务级超时、服务停止和模型错误保持可区分的错误信息。
- 所有性能结论都能由阶段计时、进程树和最终 API 结果相互核对。

## 10. GPU 迁移决策门禁

满足以下任一条件后，进入 GPU 小规模试点：

- 持久 Worker 和输入复用后，整例仍超过已确认的临床 SLA。
- 六模型累计 `inference_seconds` 占整任务总耗时超过 50%。
- 业务需要提高连续任务吞吐或并发量，且 CPU 已成为明确容量瓶颈。
- CPU 线程、I/O 和视频路径优化后，模型前向仍是最大单项耗时。

GPU 试点要求：

- 先单机、单 Worker、单任务，不直接增加并发。
- CUDA 运行时与当前 `torch 2.4.0+cu121` 兼容；实际部署前重新核对驱动与依赖。
- 先测试一个模型，再测试六模型常驻或单模型槽。
- 使用同一 DICOM、权重、预处理、后处理和算法版本做 CPU/GPU 对照。
- 记录冷/热耗时、每阶段耗时、显存峰值、GPU 利用率、结果差异和 CPU 回退耗时。
- 在取得六模型显存报告前，不锁定 8–12 GB 或其他采购规格。

如果 Worker 源码、模型、依赖或设备路径会改变可复现行为，应生成新的不可变正式发布版本；不得继续沿用旧版本标识。

## 11. 发布、灰度与回滚

1. 保留当前逐模型子进程模式作为回退路径。
2. 先在测试环境使用同一 DICOM 做影子对照，不让新 Worker 结果覆盖基线结果。
3. 算法负责人确认结果容差、临床负责人确认视频契约后再生成正式发布清单。
4. 首次发布维持单 Worker，监控耗时、RSS、失败率和自动重启次数。
5. 若出现结果不一致、内存泄漏或恢复失败，切回旧模式；已创建任务继续保留其创建时算法版本。

建议新增但尚未实现的配置开关：

```text
MEASUREMENT_WORKER_MODE=subprocess|persistent
MEASUREMENT_MODEL_RESIDENCY=single_slot|preload_all
MEASUREMENT_VIDEO_MODE=synchronous|asynchronous
```
